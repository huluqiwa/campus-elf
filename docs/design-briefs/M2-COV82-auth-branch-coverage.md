## 1. 目标

把 `app/auth` 的**分支覆盖率 CI 读数**从 412/506 = 81.42% 抬到 ≥ 82%（82% 需 415 条 covered，即净增 3 条），并顺带把 TD-234 那条「CI 比本地少 1 条」的口径差**定性收口**——它现在挂着一条已经不成立的描述。

不做什么：不改生产代码的行为（除非发现真实缺陷，见 §7(c)）；不动 `THRESHOLDS["app/auth"]` 的 80（是否抬到 82 是另一件事，见 §7(b)）；不碰前端；不碰 `backend/` 之外的包。

### 现状事实（全部实测，附来源）

- **CI 读数 412/506 = 81.42%**：取自 187g-A 合并后的 main 推送 CI（run `40943258297`）上传的 `coverage.json` 产物，逐文件汇总而得；82% 需 415 条、**缺 3 条**（按 `backend/scripts/check_coverage.py:82` 的 `covered / total * 100` 反算，`ceil(0.82 × 506) = 415`）。
- **逐文件缺支数**（同一份 CI 产物）：`service.py` 缺 72/350、`principal.py` 缺 6/32、`mfa.py` 缺 4/16、`passwords.py` 缺 3/16、`revocation.py` 缺 3/16、`sessions.py` 缺 3/42、`tokens.py` 缺 3/28。
- **CI runner 是 CPython 3.13.18**（安装日志 `Using CPython 3.13.18` 与产物头 `coverage: platform linux, python 3.13.18-final-0`），**本地是 3.13.13**；coverage.py 两边都是 **7.17.0**（CI 侧 `coverage==7.17.0`、pytest-cov 7.1.0）。→ 若仍有 ±1 口径差，变量只剩**解释器补丁版本**与**平台**。
- **TD-234 的原记载在本次产物里不成立**：它写「`682 → 683` 弧记为 missing，而同一份产物里 683 行又记为已执行，两者不能同时成立」。当前这段代码已随 187f/187g 的改动移到 `686/687`，产物里 **687 行在 `missing_lines`、弧 `686 → 687` 在 `missing_branches`**，两者自洽——真实含义是「`_load_roles` 的租户缺参防御分支从来没走过」，不是报告矛盾。这条要么定性、要么改写成复核结论，不能继续挂着错描述。

## 2. 候选方案

### 方案 A（推荐）：补 5 条真实安全分支的确定性用例，净增 ≥3 条、留 2 条余量

做法：按下表逐条写用例，每条**独占**一条目标弧（用「加用例前后逐弧 diff」证明该弧从 missing 变 executed），断言落到错误码／HTTP 状态／审计行／Redis 或 DB 状态，而不是「函数没炸」。

| # | 目标弧 | 这条分支在防什么 | 用例怎么打 |
|---|---|---|---|
| 1 | `mfa.py:58 → 59` | 租户 realm 铸造 MFA 令牌时 `tenant_id is None` → `ValueError`：缺租户参数的 MFA 状态令牌**绝不能发出去**，否则它就成了跨租可用的凭据 | 直接调铸造函数，`realm="tenant"`、`tenant_id=None` |
| 2 | `mfa.py:60 → 61` | 平台 realm 携带 `tenant_id` → `ValueError`：两个 realm 的令牌命名空间互斥，混用会让平台令牌落到租户空间 | `realm="platform"` 且传一个 tenant_id |
| 3 | `principal.py:285 → 286` | `identity.token_version != claims.token_version` → 401「登录已失效，请重新登录」：**改密／登出／停用后旧访问令牌必须立刻失效**，这是 auth 的承重墙之一 | 在库里把该用户的 token_version 直接 +1（保留会话标记），拿改动前签发的旧令牌打受保护接口——走真实改密链路会先被会话撤销（`264 → 267`）拦下，`285 → 286` 是 Redis 不可用（fail-open）或会话标记残留时才兜底的那一支 |
| 4 | `principal.py:271 → 272` | 租户主体的 `claims.tenant_id is None` → 401「令牌无效」：租户 audience 的令牌没有租户归属时**默认拒绝**，不能退化成"查得到算运气" | 手工签一枚缺 tenant_id 的租户 audience 令牌 |
| 5 | `tokens.py:215 → 216` | `amr` claim 不是 list → 返回空集（`_parse_amr`）：伪造的 `amr` 形状不对就按**未完成 MFA** 处理，不能把字符串拆成字符、也不能当成已验证 | 直接签一枚 `amr` 为字符串/dict/数字/null 的访问令牌，交给 `decode_access_token` 解析 |

备选（若某条实际已被别的用例顺路覆盖而不再缺，按顺序替补）：`sessions.py:145 → 146`（租户会话操作缺 tenant_id → `ValueError`）、`service.py:686 → 687`（`_load_roles` 租户缺参）、`revocation.py:228 → 229`（超过 `max_attempts` 直接放弃，防限流被绕）。

- 优点：每条都是「没测就等于没防护」的路径，符合 §1.7 的业务结果断言；全部**确定性**（构造入参或 DB 状态即可，不靠并发时序），不会再制造 TD-221 那种读数漂移。
- 缺点／成本：写 5 条比写 3 条多；第 3 条要走真实改密/停用链路，夹具成本略高。
- 风险：低。只加测试文件；若某条用例把既有 fixture 状态污染（同一 worker 内串味），表现为读数不升反降，逐弧 diff 能立刻定位。
- 对 spec/design 的影响：无。只回写 `docs/tech-debt.md`（TD-221／TD-234）与 `docs/handoff.md`／README 的门禁读数。

### 方案 B：只补 3 条最便宜的分支，刚好过线

做法：挑 `service.py:2084 → 2085`（`RuntimeError("activate_mfa 未返回令牌")`）这类 monkeypatch 就能造出来的防御支，凑满 415。
- 优点：最快、最省。
- 缺点：为数字而测——断言的只是"代码里确实有一句 raise"，对业务正确性零覆盖；**余量 0**，下次动 auth 掉一条分支就红（TD-221 已经吃过「81% 余量 0 条、首跑必红」的亏）。
- 风险：把 82% 变成一个纸面数字，正是 §1.7 禁止的做法。→ 不选。

### 方案 C：先把本地与 CI 的解释器对齐，再决定补几条

做法：`.python-version` 钉到 3.13.18，让本地读数与 CI 一致。
- 优点：从根上消除"两个数字"的争论。
- 缺点：**它不解决"缺 3 条"这个事实**（补测试仍然必须做）；且改版本会影响所有人重新下载解释器与重建 venv，属于环境级动作，不该塞进一个测试点。
- 结论：不整体采纳，但**吸收它的第一步**——本点用 `uv run --python 3.13.18`（不入库、只在本地临时）复跑同一批用例，作为 TD-234 的定性手段；是否正式钉版本留给 M2 边界评审。

### 方案 D：直接把 `THRESHOLDS["app/auth"]` 从 80 抬到 82 当"达标"

- 拒绝：门槛是**防倒退的下界**，读数没到就抬等于让 CI 常红；且 TD-221 定的规则是「按 CI 最低观测向下取整」，本仓所有门槛调整只认 CI 产物。

## 3. 选择结论

- **选择 A**（内含 C 的定性步骤作为第 0 步）。
- 理由：本点的真实目的有两个——把 auth 的防护空洞填上、把 82% 这条线站稳。A 同时满足且留余量；B 只满足数字；C 只满足口径；D 是作弊。
- 不选其他方案的理由见各方案「结论」行。
- 是否需要改 spec/design：**不需要**。需要回写的文档：`docs/tech-debt.md`（TD-234 定性结论、TD-221 的 82 目标尾差）、`docs/handoff.md` §1 与 README 的门禁读数、`docs/review-log.md` 的审查记录。
