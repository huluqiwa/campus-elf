## 0. 现状（2026-11-08，均已在代码/迁移核实）

- 状态机 `app/kb/status.py` 止于 `TEST_PASSED`（出边只有 →TESTING 重测）；`TEST_PASSED → PUBLISHED`、`PUBLISHED → OFFLINE/DELETED` 未实现。
- `kb_index_versions` 已建（KB-03A，唯一 `(tenant_id, document_version_id)`），**已预留** `published_at`/`retired_at` 列与 `published`/`retired` 状态值；`kb_publish_aliases` 表**未建**。
- Qdrant collection per version 已交付（`indexer.collection_name` = `tenant_{hash}_kb_v{version_id}`；迁移注释明确「alias 是 KB-05」）；Qdrant named alias 未使用。
- 权限码已存在：`school.kb.publish`（发布/回滚/下线）、`school.kb.delete`（删除）；无新码需求。
- 会话模型（`conversations.pinned_kb_version_id`）属 M4 未建——「旧会话固定」在本点只能验证到数据基础层（见 D5/§5）。
- 文档表 `kb_documents.status` 与当前版本状态一致（design §4.3），发布/下线/删除需同步双表。

## 1. 目标与验收（spec :288-292 逐条 → 本点覆盖）

| spec 验收 | 本点覆盖 |
|---|---|
| Given 新版本测试通过，When 发布，Then alias 指向新 collection | ✅ 端点 + alias 行 + Qdrant named alias 原子切换；「新会话用新版本」= M4 按 active 解析（本点提供解析数据） |
| Given 发布/回滚期间，When 200 并发请求，Then 零 5xx，引用版本正确 | ✅ 业务场景测试：切换期间 200 并发检索解析，断言零 5xx + 每个响应版本 ∈ {旧, 新}（不出现第三态/解析失败） |
| Given 下线/删除，When 旧会话继续提问，Then 仍可引用旧版本；7 天后清理 | ◑ 可验证部分：collection 保留 + `retired_at` 标记 + active 解析 fail-closed；「旧会话仍可引用」与 7 天清理分别依赖 M4 会话 / M6 清理 job（TD-303） |
| Given 回滚，When 新会话提问，Then 使用回滚后的版本，缓存失效 | ✅ 回滚切 alias；「缓存失效」依赖 M4 缓存（TD-304），本点保证 Key 约定（`tenant:kb:version`）与 alias 数据正确 |

状态机不变量（state-machines §3）：TEST_PASSED 才能发布；发布/回滚只切 alias 不改分块；同文档活跃指针唯一。

## 2. 候选方案

### D1 alias 粒度与命名（⚠ 需修订 design §7.4）

- **A（推荐）：每文档一个 alias**。`kb_publish_aliases` 一行一文档（唯一 `(tenant_id, document_id)`），Qdrant named alias 命名 `tenant_{tenant_hash}_kb_{document_id 短哈希}_active`；发布 = upsert 行 + Qdrant alias 原子指向新 collection（同一事务语义：库行与 alias 先后写，行是事实来源，alias 失败可重建）。
  - 优点：与 KB-03A 已交付的 collection-per-version 物理模型一致；回滚/发布互不影响其他文档；`kb_publish_aliases.kb_id` 列与 design §4.3 原意吻合。
  - 缺点/影响：design §7.4 的 `tenant_{tenant_hash}_kb_active`（租户单名）在物理上不成立（Qdrant alias 指向单 collection，租户多文档必有多个活跃 collection），**需回写 design §7.4 为文档级命名**；M4 检索按「活跃集合解析」逐文档查询。
- B：租户单 alias + 合并 collection。缺点：推翻 KB-03A 交付物（collection 粒度重构），改动面波及 chunker/indexer/test 沙箱。不选。

### D2 回滚语义

- **A（推荐）**：`POST /school/kb/versions/{version_id}/rollback` 的 path `version_id` = **目标版本**（要切回的旧版本）。guard：目标 `PUBLISHED` + 目标 collection 存在（Qdrant `collection_exists`）+ 目标 ≠ 当前活跃；当前活跃版本**保持 PUBLISHED**（蓝绿共存）。等效「任意已发布版本间切换」，无需发布历史表。
- B：只允许回滚到「上一版」（需 alias 行存 prev_version_id 或历史表）。缺点：多一份数据职责，灵活性低；「回滚上一版」UI 可由前端按 A 组合实现。不选。

### D3 下线/删除语义（按状态机，无备选分歧）

- 下线：`PUBLISHED → OFFLINE`（终态，无重新发布出边——重发走新版本）。若是活跃版本：撤 alias 行 + `kb_index_versions.retired_at` 标记；`kb_documents.status` 同步 OFFLINE。
- 删除：仅 `PUBLISHED → DELETED`（软删；状态机唯一删除出边；REJECTED/SCAN_FAILED/FAILED 等清理归 KB-06/07 或运维，不在本点扩状态机）。活跃版本删除：撤 alias + retired 标记（新会话解析不到 = fail-closed 404）；collection 保留（清理归 M6）。
- 两者的「不影响在线会话」在 M3 验证到「collection 未删除、旧 version 数据完整可检索」这一层。

### D4 ACL 发布门禁缺口（⚠ 须用户知情确认）

- state-machines 不变量（:86/:98）要求「已确认 ACL 才能构建/发布」，但 KB-09（`kb_document_audiences` 表 + `acl_confirmed` 列 + 接口）未实现——KB-03A 构建侧同样未设此门禁。本点发布门禁**只做 TEST_PASSED**；ACL fail-closed 随 KB-09 落地（构建 + 发布同批补），登记 TD-302。
- 需要确认：M3 退出标准中「ACL fail-closed」项延后至 KB-09 验收时核验。

### D5 缓存失效与 7 天清理的 MVP 边界

- **A（推荐）**：缓存属 M4（Redis KB 检索缓存未存在）——本点保证 alias/解析数据正确 + 缓存 Key 约定沿用 design §7.6（`tenant_id:kb_id:version_id:*`），失效语义登记 TD-304 随 M4 兑现；retired collection 清理 job 延后 M6（TD-303）——M3 无会话，「保留至会话结束」不可计算，提前写清理 cron 无法验收。
- B：本点顺带写 7 天清理 cron。缺点：无会话数据支撑、属提前硬化。不选。

### D6 后端/前端切分

- **A（推荐）：本点纯后端**（迁移 + 状态机 + 4 端点 + 审计 + 业务场景 + TD-292 全栈 E2E）；前端发布/回滚/下线/删除按钮随 KB-05B（下一简报，与 KB-01A/B、KB-04A/B 节奏一致）。
- B：全栈一个 PR。缺点：diff 过大（迁移 + 状态机 + 4 端点 + Vue 按钮 + mock E2E）。不选。

## 3. 选择结论

- **D1 A（每文档 alias，design §7.4 回写随本 PR）/ D2 A（回滚 = 切到任意 PUBLISHED 目标）/ D3 按状态机口径 / D4 门禁缺口 TD-302 + 用户知情 / D5 A / D6 A（纯后端先行）**。
- D1 触及 design 修订（alias 命名），按 AGENTS.md §1.2 先经本简报确认、合入时同步回写 design.md。
