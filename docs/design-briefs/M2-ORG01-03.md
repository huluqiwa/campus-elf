## 1. 目标

1. 落地组织数据模型：`teachers`、`students`、`classes`、`courses`、`teacher_class_courses`（design §4.2 已定义形态），手动 CRUD 接口（design §5.4）。
2. 打通 **RBAC-02 的 class/course 数据范围**（TD-151，机制已确认：方案 A 授权行+同事务同步）：教师按任课/班主任/辅导员关系看对的人，学生只见自己——这是 milestone §5.4「教师只看所任课班级/本人；班主任/辅导员范围正确」的交付点。
3. 为本里程碑后续功能点铺路：ORG-02 导入写这些表，ORG-05 部门树挂 teachers.department_id，M3 KB-09 人群选择器用班级/课程/年级。

**不含**：ORG-02 导入、ORG-04 身份证加密实现（仅预留列位）、ORG-05 部门树、B 端前端页面（集中在 M2 末位功能点）、账号删除状态机（M5 DEL）。

## 2. 候选方案

### 决策 D1：class/course 数据范围的实现机制（本简报最关键决策）

**方案 A（推荐）：授权行机制 + 关系写路径同事务同步**
- 做法：完全复用 M1-E2 的 `data_scopes`（scope_type 已含 class/course）。「任课/班主任/辅导员」关系的创建与变更在**同一事务**内写/删对应用户的 class 范围行（教师→所任教班级、班主任/辅导员→所管班级、学生→self）。每请求范围解析、fail-closed、热更新、仓储谓词注入零改动。
- 优点：单一机制（角色行 ∪ 用户行）覆盖全部范围类型；范围变更天然可审计；每请求零额外 join；M3 KB-09 人群、M4 AI-10 人群过滤直接消费同一张表；TD-151 的「归属列语义」落到同步函数一处。
- 缺点/成本：关系表与范围行**双写**，一致性靠同事务 + 唯一约束兜底；需写同步函数并全量测试（漏写=范围错，属安全项）。
- 风险：同步函数遗漏某条写路径 → 范围过期。缓解：业务场景测试覆盖全部变更路径（新建/改派/删除/班级解散），并加「关系表与范围行一致性」对账单测。
- 对 spec/design 影响：无（design 的 data_scopes 定义本就含 class/course）。

**方案 B：范围实时关系推导（无范围行）**
- 做法：ScopeDecision 解析时按 user_type join `teacher_class_courses`/`classes` 动态算班级集合；data_scopes 只留 school/self。
- 优点：单一事实源，无双写。
- 缺点：破坏 M1-E2「解析不到=空集」的 fail-closed 口径（需为关系型范围另立语义）；每请求多 join（人员列表、检索过滤、人群判定都走）；M3/M4 的人群解析器要写两套（授权行 + 关系推导）；范围变更不经过 data_scopes，审计口径要另建。
- 风险：M3 检索强制过滤是安全红线，解析路径翻倍=翻倍出错面。

### 决策 D2：班主任/辅导员的权威源

design §4.2 在 `classes`（head_teacher_id, counselor_id）与 `students`（同两列）**都**放了列。二选一：

- **方案 A（推荐）：权威在 `classes`，`students` 不落冗余列**。学生响应里的班主任/辅导员字段由服务层 join 班级聚合展示；换班主任只改一处。偏离 design 表定义（删 students 两列），需记录。
- 方案 B：按 design 双列落库 + 服务层双写同步。代价：两处真相、不一致对账，无收益。

### 决策 D3：身份证列位

- **方案 A（推荐）**：建表时预留 `id_card_enc/id_card_hmac/id_card_mask`（nullable，**本点无任何读写路径**），ORG-04 只做加密、掩码、权限+理由+审计与接口——表结构一次定型，避免二次迁移。
- 方案 B：本点不建列，ORG-04 自己加迁移。表定义分裂在两个迁移，回滚链更长。

### 决策 D4：档案与账号的关系

- **方案 A（推荐）**：档案与账号 **1:1 同建**——创建教师/学生档案即创建 `users` 行（user_type 对应、初始状态 must_change_password=true，与 C 端登录链路一致）；停用档案=停用账号（status 联动）。
- 方案 B：档案可无账号（纯档案）。会分裂「谁能登录」的判定，M5 请假审批人解析也要处理无账号档案，复杂度后移。

## 3. 选择结论

- D1 选 A（授权行+同事务同步）、D2 选 A（权威在 classes）、D3 选 A（预留列位）、D4 选 A（1:1 同建）。
- 理由：D1 是安全机制选型，复用已验收的 M1-E2 机制风险最小、审计/热更新/fail-closed 全部继承；D2/D3/D4 都是「单一事实源优先」。
- 是否需要改 spec/design：D2 偏离 design §4.2 的 students 两列（删冗余），经确认后回写 design.md；其余不改。

## 9. 实现结果

**交付物**：迁移 `c9d5f1e3a7b9`（五表 + RLS + 授权 + `uq_data_scopes_user_class` 部分唯一索引）；`app/db/models/org.py`；`app/rbac/scopes.py`（DataScopeContext.class_ids + class 谓词）；`app/db/repository.py`（list_cursor + class_scope_factory）；`app/auth/principal.py`（class_ids 贯通 Identity→Principal）；`app/org/scopes_sync.py`（期望对推导/差量对账/同事务同步/成员工厂）；`app/org/service.py`（CRUD + 审计 + 初始密码）；`app/api/school_org.py`（13 个端点，cursor 分页一律 `CursorError`→400）；personnel 服务接 class 工厂；启动自检 REQUIRED_RLS_TABLES 纳入五表。

**测试**：单元 5（对账/cursor）、集成 8（唯一约束/1:1/RLS 隔离/范围行同步/回滚）、业务场景 BS-M2-01（排课→范围可见→调岗立即生效→越权 404+审计→学生 403→仅 self 可见自己）。

**实现期偏差（已按确认口径处理，审查对照用）**：
1. 班主任/辅导员：API 与响应统一为**教师档案 id**（前端选老师），服务层解析为 users.id 落列（D2 存储口径）；审计 before/after 同口径（映射回档案 id）；
2. `/school/students` 回显学号/登录名（B 端管理通道）；M1-E2 口径 ⑥ 仍只钉 `/school/personnel`；
3. 矩阵 §5 行 173：学生/教师（C 端）无 `personnel.view` → 学生调用 403；「本人」由 self 范围承载（无任课教师仅见自己一行，非空集）；
4. 班级/课程/任教维护用 `school.org.manage`（矩阵未给组织关系单列码，取组织管理语义）；
5. TD-070 部分收口：新接口全 cursor，`/school/personnel` 信封迁移随 B 端页面功能点；
6. 新登记 TD-174（范围行双写一致性，无 DB 级联动，M2 末评审是否补对账任务）；
7. `teachers.department_id` 未随本迁移预留：其外键目标 `departments` 表在 ORG-05 才建，
   无法提前建 FK；ORG-05 出一次加列迁移（取舍记录，design §4.2 不变）；
8. 班级/课程/任教维护取 `school.org.manage`（矩阵 §5 行 175 描述扩展为「组织结构维护」）；
