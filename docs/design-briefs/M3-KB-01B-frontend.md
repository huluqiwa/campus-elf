## 0. 现状核对（读代码得到的事实）

**后端契约（KB-01A 已合并）**

- `POST /api/v1/school/kb/documents`（`school.kb.upload`）：multipart `files[]`（1–15 个）+ 必填 `Idempotency-Key`（8–128 位 `[A-Za-z0-9._:-]`）+ 可选 `metadata`（JSON 数组，长度=文件数，元素 `{title?, tags?, description?}`）；整批原子，201 返回 `{batch_id, replayed, documents[]}`。
- `GET /api/v1/school/kb/documents`（`school.kb.view`）：cursor 分页，`limit` 默认 20、上限 100；按数据范围过滤（`school` 看全校 / `self` 只看自己上传）。
- `GET /api/v1/school/kb/documents/{id}` 与 `GET …/{id}/versions`（`school.kb.view`）：详情、版本列表（cursor 分页）；范围外/跨租一律 404。
- 文档 `status` 只有三档：`UPLOADED`（扫描中/待重试）、`PENDING_APPROVAL`（扫描通过，可提交审批）、`SCAN_FAILED`（感染/完整性失败）；扫描状态是**派生**的 `scan.{state,engine,signature,error_code,attempts,scanned_at}`，`state ∈ pending|error|passed|infected|skipped`（派生逻辑 `backend/app/kb/service.py:181-193` `derive_scan_state`；响应模型 `backend/app/api/school_kb.py:44-52`）。
- 错误体统一 `{detail: {code, message, …extra}}`；批量校验失败 `code=BATCH_VALIDATION_FAILED` 且 `extra.files=[{index,filename,code,message}]`（`backend/app/kb/service.py:298-312`）；幂等冲突 409 `IDEMPOTENCY_KEY_REUSED`；413 由中间件返回 `{detail: "..."}`。
- 限制：15 个/批、50MB/文件、300MB/批、0 字节拒绝；白名单 `.pdf/.md/.txt/.docx/.pptx/.ppt`（`backend/app/kb/validation.py`）。

**权限事实（决定页面结构）**

- `teacher_b_end` 出厂默认**只有** `school.kb.upload`，**没有** `school.kb.view`（`backend/app/rbac/seeds.py:116`）；`school_admin` 出厂默认有 `school.kb.view`、**没有** upload（`seeds.py:102`）；校方超管两者都有。
- 权限码早于本点存在（`backend/app/rbac/catalog.py:71-72`），本点**不新增权限码、不改种子、不改矩阵**。
- 前端守卫/菜单只做体验层：路由 `meta.permission` + `AdminLayout` 菜单按 `auth.user.permissions` 过滤（`frontend/apps/admin/src/router/index.ts:55-119`、`AdminLayout.vue:17-26`）；真正边界是后端逐请求 403。

**前端既有模式（本点复用，不新造轮子）**

- API 域工厂只依赖 `session.request`；multipart 上传不得手设 `Content-Type`（`frontend/packages/api-client/src/imports.ts:44-70`）。
- 页面直接 import 单例（`frontend/apps/admin/src/api.ts`）；错误提示 `reportError`（403 交给全局，不叠第二条）或 `toUserMessage`（`error-toast.ts`、`ImportsView.vue`）。
- 列表：cursor「上一页/下一页」游标栈，不伪造页码（`PeopleView.vue:32-95`）；异步任务轮询 + 组件卸载清理（`ImportsView.vue:37-96`）。
- 判据纯函数层 + 单测（`rbac-logic.ts` / `account-logic.ts` / `logic.ts` 的既有做法）；mock E2E 手抄后端判据并注明行号（TD-253）。

**已知欠账（与本点相邻）**

- TD-259/260/261（已由 PR #33 → `75c8a08` 收口）原定「M3 首个前端点」，但三条都在**权限账号页**（`account-logic.ts` / `PermissionAccountsView.vue`），与 KB 页面无代码交集。
- TD-248（前端复刻后端格式校验）、TD-253（mock 手抄判据）是**既有口径**，本点继续沿用其风险控制方式，不新开重复条目。

## 1. 目标

让校方管理员与教师能在 B 端完成 KB-01 的用户侧闭环：

1. 教师/超管批量选择文件 → 本地预检 → 填写可选元数据 → 上传 → 看到本批次结果与扫描状态；
2. 持 `school.kb.view` 的人浏览文档列表、打开详情与版本列表、看到扫描结论（含感染/故障/开发跳过）；
3. 无权限入口不出现、直连 URL 进 403；后端仍是唯一权威边界。

**验收（本点）**

- 上传限制与后端同口径：>15 个、单文件 >50MB、合计 >300MB、空文件、非白名单扩展名在**发请求前**拦截；后端 422 逐文件错误原样展示。
- 同一次提交的网络重试复用幂等键；文件或元数据一改就换新键；201 `replayed=true` 明确提示「未创建新文档」。
- 列表/详情正确显示三档文档状态与五种派生扫描状态；未知档位显示原码，**绝不默认成「通过/正常」**。
- `engine=dev-skip/dev-degraded` 用警告样式明示「未真实扫描」，不得显示成绿色通过。
- 教师（只有 upload）看不到文档列表菜单、直连 `/kb/documents` 进 403；校方管理员（只有 view）看不到上传入口。

## 2. 候选方案

### D1 页面结构与导航

- **方案 A（推荐）：两个独立路由**——`/kb/documents`（`school.kb.view`）与 `/kb/upload`（`school.kb.upload`），菜单各一项。
  - 优点：与后端两个权限码一一对应；教师只有 upload 时菜单只出现「上传文档」，校方管理员只有 view 时只出现「知识库」；路由守卫天然表达权限。
  - 缺点：两个入口，上传后要跳列表才能看到全量；上传结果在本页展示，不影响任务完成。
- 方案 B：单页双 Tab（权限都不足时隐藏 Tab）。优点一个入口；缺点是路由只能挂一个权限码，另一个 Tab 的权限只能页面内判，直连与菜单语义都会变糊。
- 方案 C：单页按权限渲染区块（无 Tab）。缺点：教师只有 upload 时页面没有列表，语义上「知识库」页却看不到知识库；不选。

### D2 上传页交互

- **方案 A（推荐）：文件表格 + 每行可选元数据（标题默认文件名去扩展名，标签逗号分隔，描述可选）**。
  - 优点：后端 `metadata` 就是按文件数组；一次 15 个也能逐个命名；不填就整段省略，走后端默认标题。
  - 缺点：界面比「只选文件」重；用可折叠的「编辑元数据」抽屉/行内展开控制视觉噪音。
- 方案 B：只上传文件、不支持填元数据。优点最简；缺点是「元数据登记」只剩文件名，运营还得等后续接口补录；不选。
- 方案 C：上传后跳详情页再编辑元数据。缺点：KB-01 没有修改元数据接口（KB-02 才做免审修改）；本点做不了；不选。

### D3 幂等键生命周期

- **方案 A（推荐）：键绑定「本次提交的签名」**。签名 = 有序文件的 `name|size|lastModified` + 元数据 JSON；签名不变的重试复用同一个键，文件/元数据任一变化就生成新键（`crypto.randomUUID()`）。
  - 优点：网络超时/断线重试能命中后端重放，不会重复建文档；改了内容不会拿旧键去撞 409。
  - 缺点：浏览器端签名用的是文件元信息，不是内容哈希（300MB 全量哈希会卡 UI）；同内容不同时间选择的文件会被当成新提交——只影响「能否重放」，不影响正确性。
- 方案 B：每次点提交都生成新键。缺点：断线重试会建出重复文档，等于没有幂等；不选。
- 方案 C：整页会话一个键。缺点：改文件后同键必 409，用户必须刷新页面；不选。

### D4 扫描状态展示与刷新

- **方案 A（推荐）：上传结果页自动轮询；文档列表页手动刷新**。
  - 上传结果页：若当前用户持 `school.kb.view`，对 `scan.state=pending` 的文档每 5s 调一次详情（最多 15 个、5 分钟后停），全部落定即停；页面隐藏时暂停。无 view 的用户（默认教师）显示静态说明：「扫描在后台进行，扫描结果由有查看权限的管理员确认」。
  - 文档列表页：不清求自动轮询（一页最多 100 行，轮询会把后端打成筛子），提供「刷新」按钮；行内 `pending` 显示「扫描中」。
  - 优点：把请求量压在 ≤15 个/5s，且只在上传后短时间内发生；列表页不会因后台 tab 长挂而持续打接口。
  - 缺点：列表页的扫描状态不是实时的；验收口径是「可见 + 可刷新」，实时 SSE 属 KB-03 构建进度，不在本点。
- 方案 B：两个页面都自动轮询。缺点：列表 100 行 × 每 5s 的放大效应；不选。
- 方案 C：都不轮询、只手动刷新。缺点：上传后要用户自己反复点，体验差；不选。

### D5 文档列表与详情

- **方案 A（推荐）：表格 + 右侧抽屉详情**（详情含基本信息、当前版本、扫描信息、版本列表「加载更多」）。
  - 优点：复用既有抽屉模式（账号页/身份证查看）；列表分页游标栈现成；不新增路由参数与深链复杂度。
  - 缺点：文档不能通过 URL 直接分享；深链需求未出现在 KB-01 验收里。
- 方案 B：独立详情路由 `/kb/documents/:id`。优点可分享/可刷新；缺点要多一条路由权限、详情页与列表页状态重复；本点不做。
- 列表列：标题、文档状态、当前版本（文件名/大小）、扫描（state+engine+签名/错误码）、更新时间；操作列「查看」。
- 不做服务端搜索/筛选：后端列表没有 `q/status` 参数；本点不造「只在当前页过滤」的假筛选。

### D6 权限与数据范围呈现

- **方案 A（推荐）：菜单/路由按码控制；页面内不再二次猜权限**。
  - 上传页：整页要求 `school.kb.upload`；上传结果里的扫描状态由后端返回，不额外请求列表。
  - 列表页：整页要求 `school.kb.view`；数据范围由后端裁剪，前端不显示「全校/本人」切换（没有这个参数）。
- 方案 B：页面内按权限隐藏按钮（路由不挂权限）。缺点：直连 URL 能看到页面骨架与报错；与既有 TD-141 口径不一致；不选。

### D7 错误呈现

- **方案 A（推荐）：按错误码分层**。
  - 本地预检失败：行内红字 + 阻止提交（不发请求）。
  - 后端 422 `BATCH_VALIDATION_FAILED`：顶部提示「整批未保存」+ 逐文件错误表（文件名/错误码/原因）；`METADATA_INVALID`/`INVALID_IDEMPOTENCY_KEY`/`NO_FILES`/`TOO_MANY_FILES`/`BATCH_TOO_LARGE` 直接显示 `message`。
  - 409 `IDEMPOTENCY_KEY_REUSED`：提示「该提交编号已被另一批文件使用」并自动换新键（下次提交生效）。
  - 413：显示后端文案（通常是批次超限），不重试。
  - 403：交给全局处理（`reportError` 不重复弹）。
  - 网络错误/503：保留当前选择与键，提示「可原样重试」。
- 方案 B：所有错误一条 toast。缺点：逐文件错误会被淹没，用户不知道该改哪个文件；不选。

### D8 TD-259/260/261 的落点

- **方案 A（推荐）：先做一个独立小 PR** `fix(admin): 收口权限账号页 TD-259/260/261`（3 处小改 + 单测/既有 E2E 复跑），再做 KB-01B。
  - 优点：兑现「M3 首个前端点」；权限账号页与 KB 页零交集，混在一个 PR 里审查面变散；小 PR 的失败面也小。
  - 缺点：多一次 PR/CI 流程（前端 CI 约 2–3 分钟）。
- 方案 B：并入 KB-01B。缺点：一个 PR 同时改权限账号页与 KB 新页，违反单点推进；不推荐。
- 方案 C：继续延后到「下次动权限账号页」。缺点：与台账「M3 首个前端点」的处置矛盾；不选。

### D9 全栈 E2E 安排

- **方案 A（推荐）：KB-01B 用 mock E2E；紧随其后单列 KB-01C 全栈 E2E 小点**（真实后端 + 真实库；扫描用 E2E 栈的 dev-skip 或加 ClamAV 容器，二选一在 KB-01C 简报里定）。
  - 优点：本 PR 的验证面是 UI 判据与契约消费，mock 足够；同时不把「UI 点没有真实后端验证」留成第二个 TD-183/192。
  - 缺点：多一个小点；全栈栈启动慢（本机约 1 分钟）。
- 方案 B：KB-01B 直接加全栈用例。缺点：要改 `deploy/docker-compose.e2e.yml`（加 ClamAV 或 dev-skip 开关）并调栈，前端 PR 的 diff 会跨到部署层；不选。
- 方案 C：不做全栈、只靠 mock。缺点：重演 M2 的欠账；不选。

## 3. 选择结论

- D1 A（两个路由）／D2 A（文件表格 + 可选元数据）／D3 A（签名绑定幂等键）／D4 A（上传页轮询、列表手动刷新）／D5 A（表格 + 抽屉）／D6 A（路由/菜单按码）／D7 A（分层错误）／D8 A（TD 小 PR 前置）／D9 A（KB-01C 全栈单列）。

### 3.1 范围内子决策（随简报一并确认）

- **菜单**：`知识库`（`/kb/documents`，`school.kb.view`）与 `上传文档`（`/kb/upload`，`school.kb.upload`），放在「部门树」之后、「批量导入」之前。
- **状态文案与颜色**（未知档位一律显示原码，不默认成安全态）：
  - 文档状态：`UPLOADED`＝「待扫描/扫描中」（info）、`PENDING_APPROVAL`＝「待审批」（success）、`SCAN_FAILED`＝「扫描未通过」（danger）、未知＝`未知状态（code）`（warning）。
  - 扫描状态：`pending`＝「扫描中/待扫描」（info）、`passed`＝「已通过」（success）、`infected`＝「发现威胁」（danger）、`error`＝「扫描故障（后台将重试）」（warning）、`skipped`＝「已跳过扫描」（**warning，不用 success**）、未知＝`未知（code）`（warning）。
  - 引擎：`clamav`＝「ClamAV」；`dev-skip`＝「开发环境跳过扫描」（warning）；`dev-degraded`＝「扫描不可用，开发环境降级」（warning）；空＝「—」。
- **元数据表单**：标题默认「文件名去扩展名」（≤200，可清空表示用后端默认）；标签逗号/中文逗号分隔、去空去重、≤10 个且每个 ≤32 字；描述 ≤1000 字。未编辑任何一行时**不发送** `metadata` 字段；只要有一行编辑，就发送与文件等长的数组（未编辑行发 `{}`）。
- **本地预检**（与后端同口径，后端仍权威）：1–15 个；单文件 ≤50MB；合计 ≤300MB；0 字节拒绝；扩展名白名单 `.pdf/.md/.txt/.docx/.pptx/.ppt`（大小写不敏感）。浏览器 `File.type` 只用于展示，不作为拒绝依据（后端按魔数判定）。
- **幂等键细节**：`crypto.randomUUID()`（36 字符，命中后端 8–128 位字符集）；提交前按 D3 计算签名；成功后清空选择与键；409 后强制下一次生成新键；422/413/网络错误保留键以便原样重试。
- **上传结果**：展示 `batch_id`（可复制）、`replayed` 提示、每份文档的标题/文件名/大小/状态/扫描；有 view 权限时按 D4 轮询；无 view 时显示静态说明。
- **列表分页**：默认 `limit=20`；游标栈上一页/下一页；`next_cursor` 为空时禁用下一页；加载失败**保留旧行但显示醒目的「数据可能不是最新（上次成功 HH:MM:SS）」横幅 + 重试**（TD-260 的教训：不做静默保留）。
- **详情抽屉**：打开即请求详情 + 第一页版本（`limit=20`）；版本列表「加载更多」按 `next_cursor` 追加；详情 404 时提示「文档已不可见」并关闭抽屉、刷新列表。
- **不做**：文档删除/重命名/标签编辑、上传进度百分比（见 TD 预判）、列表服务端搜索/筛选、文档深链、审批按钮。

## 7. 高风险确认

- **是否属于高风险功能**：是（租户数据展示、上传入口、恶意文件相关状态、权限门禁体验层、幂等重试）。后端边界已由 KB-01A 覆盖，本点风险集中在「界面误导」与「重复提交」。
- **需要用户确认的点**（推荐项在前）：
  1. **两个路由而不是一个页面**：教师只看到「上传文档」，校方管理员只看到「知识库」；直连无权限 → 403。
  2. **上传可以填元数据**（标题/标签/描述，按文件），不填则整段省略走后端默认。
  3. **幂等键随「文件+元数据」变化更换**：网络重试复用，改内容换新键；201 `replayed=true` 明确提示。
  4. **上传页自动轮询扫描状态、列表页手动刷新**；无 view 权限的教师只看到「后台扫描中」的静态说明。
  5. **dev-skip / dev-degraded 用警告样式**，绝不显示成「已通过」；未知状态显示原码。
  6. **TD-259/260/261 用一个前置小 PR 先收口**，再做 KB-01B。
  7. **全栈 E2E 单列 KB-01C**（本点只做 mock E2E），不留 M2 式的 UI 验收欠账。
- **确认结论**：用户 2026-10-31 确认全部按推荐项执行（D1–D9）。D8 的前置小 PR #33（TD-259/260/261）已于 2026-10-31 合并为 `75c8a08`；下一步开 KB-01B 分支（尚未开始）。

## 8. 审查对照

- 审查时重点验证：权限码与路由/菜单一一对应（教师 upload-only 无列表入口、直连 403）；幂等键在「签名不变复用、变化换新」上的每个分支；上传整批原子错误展示（逐文件、不隐藏）；未知/开发跳过状态不显示为安全态；轮询定时器在卸载/隐藏/超时/权限不足时确实停止；列表加载失败有可见的「非最新」提示；抽屉 404 处理；所有请求路径与后端契约逐字段对齐；mock 判据注释指向后端行号（TD-253）。
- 允许的偏差：本地预检只覆盖扩展名/大小/数量，不做魔数/ZIP 炸弹（后端权威）；不做上传字节进度（TD-280）；列表无服务端筛选（TD-279）。
