## 1. 目标

1. **审批链路**：`PENDING_APPROVAL` 版本可提交审批（显式端点，不是扫描后自动开单）；审批人通过/驳回；驳回理由必填；提交人/上传者不能自批；审批记录含提交人/审批人/时间/结果/理由/**版本快照**；提交人可撤销待审单。
2. **构建门禁**：只有 `APPROVED` 能创建构建任务；`PENDING_APPROVAL`/`REJECTED`/其他状态调用构建接口 → 409 + 审计 + **不产生任务行**；`APPROVED` 创建成功 → 任务行 `BUILD_QUEUED`；同一版本同时最多一个活跃构建任务（部分唯一索引兜底并发）。
3. **审批中心最小实现（APV-01 子集 + APV-02）**：类型注册表（种子只 `KB_DOCUMENT`）、审批单/步骤/动作三表、待办/已办/详情三个只读接口、通过/驳回/撤销三个写接口；全部租户隔离 + FORCE RLS + 审计。
4. **元数据免审通道**：`PUT /school/kb/documents/{id}` 改标题/标签/描述——不重审、写前后值审计（D4）。
5. **TD-277 收口**：上传幂等指纹并入 metadata 规范串，同键同文件不同 metadata → 409（不再静默吞改动）。

**验收（本点，全部断言业务结果而非 HTTP 200）**

- 提交：非 `PENDING_APPROVAL` 提交 → 409 `KB_NOT_SUBMITTABLE`；已有待审单再提交 → 409；成功后 `approval_requests` 出现 PENDING 单，payload 含版本快照（version_no/source_hash/filename/size/mime/scan_engine/文档标题），审计 `school.kb.approval.submitted`。
- 通过：审批人（持 `school.kb.approval`、非提交人非上传者）通过 → 版本与文档状态 `APPROVED`（事务内双写）、请求 APPROVED、审计 `school.kb.approval.approved`；自批 → 403 + 审计 `school.kb.approval.denied`；无码 → 403（`auth.permission.denied`）。
- 驳回：理由缺失/空白 → 422；驳回后版本与文档 `REJECTED`、理由落审批单、审计；REJECTED 后再提交 → 409。
- 撤销：提交人撤销自己的 PENDING 单 → CANCELLED，版本保持 `PENDING_APPROVAL` 可再提交；非提交人撤销 → 403；审计。
- 构建门禁：`PENDING_APPROVAL`/`REJECTED` 调构建 → 409 + 审计 + `kb_build_jobs` 零行；`APPROVED` → 201 + `BUILD_QUEUED` 行 + 审计；并发二次创建只有一个成功（部分唯一索引），另一个 409；跨租 version_id → 404。
- 元数据：改标签/描述 → 200、文档字段更新、**版本状态不变**、审计含前后值；范围外文档 → 404。
- TD-277：同键同文件不同 metadata → 409；同键同文件同 metadata → 重放原批次。
- 租户边界：审批三表带 FORCE RLS；跨租审批单/构建任务访问一律 404。

## 2. 候选方案

### D1 功能点切分

- **方案 A（推荐）：本点只做后端（KB-02A），审批中心前端为下一功能点（KB-02B）**。
  - 做法：本 PR 只含迁移 + `app/approval` 引擎最小实现 + `app/kb` 门禁 + 测试；前端页面、提交审批按钮、驳回理由展示、构建按钮全部留给 KB-02B。
  - 优点：与 KB-01A→B→C 节奏一致；后端 diff 可独立审查（迁移 + 状态机 + 权限 + 审计集中在一次审查里）；E2E 留到有 UI 的一侧做才有意义。
  - 缺点/成本：本点合并后没有可见界面（用集成/业务测试证明，`school.approval.todo` 等接口暂无消费者）。
  - 风险：无——接口契约按 design §5.10 实现，前端点只是消费。
- 方案 B：审批前后端一个 PR。
  - 缺点：迁移/状态机/权限/审计 + Vue 页面 + mock E2E 混在一个 diff，审查面过大；KB-01B 的先例证明分开更可控。不选。

### D2 构建门禁的落点（KB-02 还是 KB-03）

- **方案 A（推荐）：本点交付 `POST /school/kb/document-versions/{version_id}/build` 最小实现**。
  - 做法：新建 `kb_build_jobs` 最小表（id/tenant_id/version_id/status/attempt/created_by/时间戳；部分唯一索引 `(tenant_id, version_id) WHERE status IN ('BUILD_QUEUED','BUILDING')` 兜底并发与 KB-03 的重试语义）；端点只做门禁判据 + 落一行 `BUILD_QUEUED` + 审计；**不投 worker、不推进状态**（KB-03 的执行器从 QUEUED 取件）。
  - 优点：spec KB-02 验收「Given APPROVED，When 创建构建任务，Then 允许，状态 BUILD_QUEUED」在本点可验证；「未审批 409 + 无任务行 + 审计」也是 AGENTS.md §4 的硬门禁，越早落越好；KB-03 拿到现成取件口。
  - 缺点/成本：迁移里多一张表；QUEUED 行在本点会滞留（没有消费者），需要在文档写明「KB-03 前任务不会推进」。
  - 风险：KB-03 实现时发现字段不够要改表——本表字段按 state-machines §4 与 design §5.6 的既有规划建，改列成本可控（Alembic 常规迁移）。
- 方案 B：本点只留 `assert_build_allowed(status)` 判据函数，端点整体归 KB-03。
  - 优点：diff 更小。
  - 缺点：spec KB-02 的两条核心验收（409+审计、BUILD_QUEUED）在本点不可验证，「构建门禁」名存实亡；门禁判据没有真实调用点，等于写了没人走的保险丝。不选。

### D3 自批禁令口径

- **方案 A（推荐）：审批人 ∈ {审批单提交人, 版本上传者} → 恒 403，不接例外开关**。
  - 做法：复用 `evaluate_self_approval`（`exception_enabled=False` 常量传入，内核不改动），判据取两者较强：`approval_requests.submitter_id` 与 `kb_document_versions.created_by` 任一命中当前审批人即 `SELF_APPROVAL_FORBIDDEN`（403）+ 审计 `school.kb.approval.denied`。
  - 优点：目录描述「上传者不得自批」与 spec §3.8「提交人不能自批」两个口径都覆盖；KB 场景没有合理自批需求（文件就摆在那里，不需要「审批自己传的」）；不接开关 = 少一个可被误开的生产配置面。
  - 缺点/成本：校方超管自己上传的文档默认无人可批（超管是唯一默认持码者），必须先把 `school.kb.approval` 显式授给某位管理员——这是矩阵本来的设计（△ 可授），文档写清楚即可。
  - 对 spec 的影响：无（spec 说「例外默认关闭」，本点 = 关闭且不提供租户侧入口；将来要开，走 M5 APV-01 完整版）。
- 方案 B：接 `approval.self_exception_enabled`（M1-E2 的平台级开关）。
  - 缺点：那个开关的语义是「平台审核学校注册」场景，让平台配置控制租户 KB 自批是跨域语义；且开启后超管可自批，审计面扩大。MVP 收益为零。不选（登记 TD，M5 APV-01 完整版再决定）。

### D4 元数据编辑的权限码

- **方案 A（推荐）：复用 `school.kb.upload`，数据范围照常收窄（self 只能改自己上传的）**。
  - 做法：`PUT /school/kb/documents/{document_id}` 挂 `school.kb.upload`，按既有数据范围谓词取文档（fail-closed）；标题/标签/描述可选更新，任一变更写审计 `school.kb.metadata.updated`（前后值）；版本状态不因元数据变更而重审。
  - 优点：权限目录 61 码不动（无矩阵/manifest/种子连锁改动）；语义成立——「能上传的人管理自己上传的文档」；校方管理员要集中管理元数据时由超管授 upload（或将来授更细的码）。
  - 缺点：粒度粗——「只给元数据管理、不给上传」的授权组合做不到；登记 TD，若运营真有此需求再走目录变更（61→62）。
- 方案 B：新增 `school.kb.metadata.edit`（目录 61→62）。
  - 缺点：目录/矩阵/rbac 单测/route manifest 四处连锁改动，为一个低敏写操作开新码，成本大于收益。不选。

### D5 审批列表与动作的数据范围口径

- **方案 A（推荐）：审批 todo/done/详情/通过/驳回按**租户级**（权限码为主判据，不按提交人数据范围裁剪）**。
  - 做法：三个只读接口挂 `school.approval.todo`，两个写接口挂 `school.kb.approval`；不套人员数据范围谓词（与 `GET /school/permission-accounts` 的 TD-237 口径同源）。
  - 优点：审批是租户级治理动作；按提交人范围裁剪会让 self 范围的持码审批人看不到任何待办（自批禁令又保证自己提交的不能自己批 → 列表恒空），功能自相矛盾；风险已由「权限码 + 自批禁令 + 全量审计」三道兜住。
  - 缺点：self 范围用户被授 `school.kb.approval` 后可审批全校提交——但授码本身就是超管的显式治理动作，与给权限账号页授码同一逻辑。
  - 对 spec 的影响：无（spec 只说数据范围管业务数据可见性，审批单归治理对象；与 TD-237 判例一致）。
- 方案 B：列表按数据范围裁剪。
  - 缺点：如上，self 范围持码者功能不可用；school/self 混合范围还要解释「为什么提交人范围决定审批可见性」。不选。

### D6 审批引擎最小集的边界

- **方案 A（推荐）：类型注册 + 单/步骤/动作三表 + 7 个端点；无附件表、无通知、无超时**。
  - 做法：`approval_types`（seed 只 KB_DOCUMENT）、`approval_requests`（含 `payload_json` 存版本快照与 `reject_reason`）、`approval_steps`（本期恒 1 步，approver 池 = 持码者，`approver_id` 在动作时落）、`approval_actions`（逐笔动作留痕）；端点 = submit（KB 侧）+ todo/done/detail + approve/reject + cancel。
  - 优点：state-machines §6 的 PENDING/APPROVED/REJECTED/CANCELLED 全覆盖；EXPIRED 依赖定时任务与通知（M5 的 MSG/cron），本点不造假实现；附件表（§4.5 第五张）在 KB 场景无主体，M5 随请假场景建。
  - 缺点：M5 做 APV-01 完整版时要加附件/通知/超时/多步审批的迁移与接口——已登记 TD-286（§6）。
  - 对 spec 的影响：无（milestone §6.2 本来就是「最小实现 APV-01/02」）。
- 方案 B：连附件表、多步审批一起建。
  - 缺点：为不存在的场景（KB 审批没有附件；多步审批无类型需要）提前建模，表结构猜测成分高，M5 大概率返工。不选。

### D7 TD-233 的落点改判

- 事实：TD-233 的 4 个文件（`test_bs_m2ui2_rbac_admin.py`、`test_bs_m1e2_scope_and_sod.py`、`test_bs_m1d2_mfa.py`、`test_auth_d2_mfa.py`）是 MFA/RBAC 审计助手口径问题，**KB-02 不会触碰它们**；按台账自身规则「若 M3 首批仍不动这些文件，必须重新指定落点，不能静默留在台账」。
- **方案 A（推荐）：改判「M3 里程碑边界评审」**——若边界评审时仍无人动过，随评审批量收口或再延后并说明。
- 方案 B：本点顺带收口（单独 commit）。缺点：混入与 KB-02 无关的测试改动，违反「一个功能点一个 PR」的既有拆分纪律（TD-187f-A 当初就是因此单独成点）。不选。
- 方案 C：立即单独开一个小 PR。缺点：为预防性加固插队，打断 KB-02 单点推进。不选。

## 3. 选择结论

- **D1 A（后端先行）／D2 A（build 端点进本点）／D3 A（自批恒 403）／D4 A（复用 upload 码）／D5 A（审批租户级）／D6 A（最小引擎集）／D7 A（TD-233 改判 M3 边界评审）**。用户 2026-11-07 确认 D1–D4 全按推荐项执行；D5/D6 按推荐默认（未提异议）。
- 对 spec/design 的影响：均无需修改——所有端点、表、状态机流转与权限口径都是 spec/design 已规划内容的落地；「例外开关不接入」「QUEUED 滞留至 KB-03」「已发布修改正文验收延至 KB-05」三条边界写进简报与 design 备注即可。

## 4. 实现顺序与 TDD 测试清单
